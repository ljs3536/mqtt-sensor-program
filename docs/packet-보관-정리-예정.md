# packet 보관 정리 (작업 예정)

상태: **예정**. 아직 코드는 바꾸지 않았다. 정할 것을 정한 뒤 진행한다.
논의: 2026-11-18.

## 왜

수신한 패킷 하나가 두 곳에 똑같이 저장된다.

```
MQTT 수신 ─┬─> CSV 큐 → CSV 쓰기 스레드 → data_csv/…csv
           └─> SQLite packet INSERT + commit (패킷마다)
                         ↑
              통계(하루 한 번)는 여기서만 읽음 → measurement
```

- CSV와 통계는 서로 만나지 않는다. 통계는 CSV를 읽지 않으므로 "CSV를 쓰는 중에 통계를 내면 문제가 생기는가"는 걱정하지 않아도 된다.
- SQLite 안에서 수신과 통계가 겹치는 것도 안전하다. 통계는 시작 순간 커밋된 id까지만 읽고, X/Y/Z가 덜 온 끝 세트는 다음으로 미루고, `stats_lock`으로 한 번에 하나만 돈다.
- 문제는 **용량**이다. `packet`은 지우지 않아서 끝없이 쌓인다.
  - 2026-11-18에 잰 크기: 패킷 약 1,600개에 DB 86MB.
  - 패킷 하나: ADXL 약 65KB(HEX 32KB + 샘플 문자열 32KB), PIEZO 약 90KB, 초음파 약 7KB.
  - 1시간 주기 MEMS 10대: 하루 약 5MB, 1년 약 1.7GB. 시험처럼 1초마다 들어오면 그 3,600배.
  - 같은 원본이 CSV에도 있으니 두 벌이다.

## 방향: 원본은 최근 것만 DB에, 오래된 원본은 CSV에

`packet`을 MAC마다 **최근 N세트**만 남기는 테이블로 바꾼다. 통계 결과(`measurement`)는 지금처럼 영구히 남는다.

| 쓰는 곳 | 바뀐 뒤 |
| --- | --- |
| 통계(하루 한 번) | 그대로. 아직 통계에 안 들어간 패킷은 N을 넘어도 지우지 않는다 |
| 센서 데이터 분석 `/studio`(DB에서 열기) | 남긴다. "최근 데이터만 본다"는 화면이 된다. 최근 N세트까지 |
| 대문 연결 판정(최근 수신 시각) | 그대로 `packet`에서 읽는다. 최근 N세트면 충분하다. 따로 테이블을 만들지 않는다 |
| 오래된 원본 보기 | CSV를 `/generator`(데이터 분석 CSV)에서 연다 |
| 보정값을 바꿔 지난 통계 다시 내기 | `python -m web_db.src.import_csv <CSV 폴더> --reset`으로 CSV를 다시 넣어 계산 |

처음에는 "통계가 끝난 패킷은 바로 지우고 `/studio`를 없앤다"도 생각했다. 하지만 그러면 `/studio`가 통계 직후에는 비고 다음 통계 직전에는 하루치가 보이는 식으로 들쭉날쭉해서, 개수로 남기는 쪽을 골랐다.

## 할 일

| # | 일 | 내용 |
| --- | --- | --- |
| 1 | 보관 개수 정리 | 통계가 끝난 뒤(또는 저장 때) MAC마다 최근 N세트보다 오래된 `packet`을 지운다. 조건: `id ≤ 통계 읽기 위치(stat_cursor)`인 것만. ADXL은 세트(`set_key`) 단위, PIEZO·초음파는 패킷 단위 |
| 2 | DB 파일 크기 | 지워도 SQLite 파일은 줄지 않고 빈 칸을 다시 쓴다. 크기가 고정되면 충분하다. 줄이려면 가끔 `VACUUM`(서버 멈춘 때) |
| 3 | CSV 상시 저장 | 오래된 원본은 CSV에만 남으므로 CSV를 끌 수 없게 한다. 설정 화면 '자동 연결 때 CSV 저장' 체크와 수신 모니터의 CSV 끄기를 없앤다 |
| 4 | `/studio` 문구 | "최근 N세트까지만 DB에 있습니다. 그 전은 데이터 분석 CSV에서 여세요" 안내 |
| 5 | 문서 | DB 명세(`packet` "지우지 않는다" → 보관 규칙), 데이터 흐름, 화면 역할 |
| 6 | 점검 | 보관 개수 넘김, 통계 전 패킷은 안 지움, 대문 판정·`/studio` 불러오기 그대로 |

## 정할 것

1. **N(MAC마다 보관 세트 수)**. 권장 50세트.

   | MAC마다 | MAC 1대 | MEMS 10대 | 1시간 주기면 |
   | --- | --- | --- | --- |
   | 50세트 | 약 10MB | 약 100MB | 약 2일치 |
   | 200세트(`/studio` 최대 불러오기 수) | 약 40MB | 약 400MB | 약 8일치 |

2. **통계 주기**. 아래 "통계 주기 검토".
3. **CSV 끄기 옵션 없애기**에 동의하는지(할 일 3).

## 통계 주기 검토

2026-11-18에 정한 것: 통계는 **하루 한 번 고정**(자정 뒤 10분 안 자동). 통계 화면의 최신화 버튼은 없앴다. 사람마다 다른 시각에 최신화하면 보는 값의 기준 시각이 달라 혼란스럽기 때문이다. 화면에는 모두에게 같은 "마지막 계산 시각"이 보인다.

더 자주 할지 검토한 내용:

| 방식 | 좋은 점 | 나쁜 점 |
| --- | --- | --- |
| 하루 한 번(지금) | 단순하다. 통계 화면 작은 그래프 한 점 = 하루 | 대문 알람이 최대 하루 늦다. 보관 N보다 하루 수신이 많으면(시험처럼 빠른 수신) 통계 전 패킷이 N을 넘어 쌓인다 |
| 매시 정각 | 대문 알람이 최대 1시간 늦다. 대기 패킷이 1시간치라 보관 정리와 잘 맞는다. 정각 고정이라 모두 같은 시각을 본다 | `measurement` 줄이 MAC마다 하루 24줄. 작은 그래프(최근 40구간)가 하루 반 정도만 보인다(일 단위 묶음 표시가 필요할 수 있음) |
| 데이터 받을 때마다 | 알람이 바로 바뀐다 | 시험처럼 1초마다 들어오면 세트마다 계산·저장이 수신 경로에 끼어든다. `measurement`가 세트마다 한 줄(하루 수만 줄)이라 지금 "구간 한 줄" 구조와 맞지 않는다. 하지 않는다 |

의견: 받을 때마다는 하지 않는다. 대문 알람을 빨리 보는 게 중요하면 **매시 정각**, 추세만 보면 **하루 한 번**으로 충분하다. 매시로 바꾸면 할 일은 스케줄러 조건(날짜 → 시각) 한 줄과 통계 화면 그래프 표시 정도다.
